注释¶
Go 提供 C 风格的 `/* */` 块注释，以及 C++ 风格的 `//` 行注释。行注释是常态；块注释多见于包注释，也可用于表达式内，或用于禁用大段代码。

出现在顶级声明之前、中间没有空行的注释，被视为对该声明本身的文档。这些「文档注释」是给定 Go 包或命令的主要文档。更多说明见 “GoDoc Comments”。

命名¶
在 Go 中，命名与其他语言同样重要，甚至还有语义效果：名字在包外是否可见，取决于首字符是否大写。因此值得花一点时间讨论 Go 程序中的命名约定。

包名¶
导入包之后，包名成为访问其内容的入口。例如：

```go
import "bytes"
```

导入方可以写 `bytes.Buffer`。若所有使用者都能用同一名字指代包内容会更有帮助，这意味着包名应当好：短、精炼、有启发性。按约定，包名用小写单词，通常单字；不应需要下划线或 mixedCaps。宁可偏短，因为使用者会反复键入该名。也不必先验地担心冲突。包名只是导入时的默认名，不必在全部源码中全局唯一；罕见冲突时，导入方可本地选用别名。通常很少混淆，因为 import 路径的文件名决定了具体是哪个包。

另一约定是：包名等于其源码目录的基名；`src/encoding/base64` 中的包导入为 `"encoding/base64"`，但包名是 `base64`，不是 `encoding_base64` 或 `encodingBase64`。

导入方会用包名引用内容，因此包内导出名字可利用这一点避免重复。（不要使用 `import .` 记法；它有时可简化必须在被测包外运行的测试，但除此之外应避免。）例如，`bufio` 包中的缓冲读取类型叫 `Reader`，不叫 `BufReader`，因为用户看到的是清晰简洁的 `bufio.Reader`。而且导入实体总是带包名寻址，`bufio.Reader` 不会与 `io.Reader` 冲突。同理，构造 `ring.Ring` 新实例的函数——在 Go 中相当于构造器——通常会叫 `NewRing`，但由于该包只导出 `Ring` 且包名就是 `ring`，于是就叫 `New`，客户端看到的是 `ring.New`。善用包结构来帮助选择好名字。

另一个短例子是 `once.Do`：`once.Do(setup)` 读起来很好，写成 `once.DoOrWaitUntilDone(setup)` 未必更好。长名字不会自动更易读。有帮助的文档注释往往比额外加长的名字更有价值。

Getter¶
Go 不自动支持 getter/setter。自己提供完全没问题，也常常合适，但在 getter 名字里加 `Get` 既不地道也不必要。若字段叫 `owner`（小写，未导出），getter 方法应叫 `Owner`（大写，导出），而不是 `GetOwner`。用大写导出名即可区分字段与方法。若需要 setter，多半叫 `SetOwner`。实际读起来很自然：

```go
owner := obj.Owner()
if owner != user {
    obj.SetOwner(user)
}
```

接口名¶
按约定，只有一个方法的接口，用方法名加上 `-er` 后缀（或类似变形）构成施事名词：`Reader`、`Writer`、`Formatter`、`CloseNotifier` 等。

这类名字很多，尊重它们及其所捕获的函数名很有益。`Read`、`Write`、`Close`、`Flush`、`String` 等有规范签名与含义。为免混淆，除非签名与含义相同，不要给你的方法起这些名字。反过来，若你的类型实现了与知名类型同义的方法，就用相同名字与签名；字符串转换方法叫 `String`，不要叫 `ToString`。

MixedCaps¶
最后，Go 的约定是用 `MixedCaps` 或 `mixedCaps` 写多词名字，而不是下划线。
